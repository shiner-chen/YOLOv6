**分析**：

- 运行时初始化包含 NPU 资源分配和权重加载到 NPU

### 2. 推理性能（NPU）

#### 单帧推理（Batch=1）

| 指标 | 值 |
|------|------|
| 平均延迟 | 12.36 ms |
| 标准差 | ±1.87 ms |
| 最小延迟 | 9.72 ms |
| 最大延迟 | 15.00 ms |
| **FPS** | **~81** |

#### Batch 推理（Batch=4）

| 指标 | 值 |
|------|------|
| 平均延迟 | 12.97 ms |
| 标准差 | ±1.38 ms |
| **吞吐量** | **308.4 FPS** |
| **单帧摊薄成本** | **3.24 ms** |

**关键发现**：
- ✓ Batch=4 延迟（12.97ms）仅比单帧（12.36ms）增加 **0.61ms**
- ✓ 吞吐量提升 **3.8x**（308 FPS vs 81 FPS）
- ✓ 单帧摊薄成本降至 **3.24ms**，证明 batch 推理非常高效

### 3. 端到端性能（推理 + 后处理）

| 组件 | 时间 | 占比 |
|------|------|------|
| NPU 推理 | 12.36 ms | 55% |
| CPU 后处理 | 10.19 ms | 45% |
| **端到端延迟** | **22.41 ms** | 100% |
| **端到端 FPS** | **44.6** | - |

**后处理细节**：
- Sigmoid 激活：~0.5 ms
- Anchor decode：~2.0 ms
- NMS（非极大值抑制）：~7.5 ms
- 其他开销：~0.2 ms

**优化建议**：
- NMS 是主要瓶颈（占后处理 74%）
- 可使用 NEON 指令优化或简化 NMS 算法
- 考虑降低 NMS 的 IoU 阈值以减少计算

## 性能对比分析

### 与预估值对比

| 指标 | 预估值 | 实测值 | 差异 |
|------|--------|--------|------|
| 单帧推理 | 2-3 ms | 12.36 ms | +9-10 ms ⚠️ |
| Batch=4 推理 | 4-6 ms | 12.97 ms | +7-9 ms ⚠️ |
| 后处理 | 0.8-1.3 ms | 10.19 ms | +9 ms ⚠️ |
| 端到端 | 5-7 ms | 22.41 ms | +15-17 ms ⚠️ |

**差异分析**：

#### 1. NPU 推理慢于预期的原因

**理论计算回顾**：
- YOLOv6n 计算量：~4.7 GFLOPs
- RK3588 算力：6 TOPS (INT8)
- 理论时间：4.7 / 6000 × 1000 ≈ 0.78 ms

**实际因素**：
1. **内存带宽瓶颈**：
   - ROI160 模型虽小，但特征图访问频繁
   - P2 尺度输出 40×40，数据传输开销大
   
2. **NPU 调度开销**：
   - 层间数据同步
   - 多核调度开销
   - 算子切换延迟

3. **模型架构特点**：
   - RepVGG 融合后单个 3×3 卷积较大
   - 双尺度输出（P2/P3）需要更多 feature map 传输
   - Split 输出模式（4 个独立张量）可能增加调度复杂度

4. **实际利用率**：
   - 理论峰值算力 vs 实际利用率差距
   - 小模型难以充分利用 3 核 NPU

**实测 12.36ms 是合理的**，考虑到：
- 小模型（3.87 MB）通常内存访问密集型
- 多输出头增加数据传输
- 实际 NPU 利用率约为理论值的 6-10%（行业常见）

#### 2. 后处理慢于预期的原因

预估基于优化的 C++/NEON 实现，但实测使用 **纯 Python + NumPy**：
- Python 解释器开销
- NumPy 数组操作非最优
- NMS 未优化（嵌套循环）

**优化潜力**：
- 使用 C++ + NEON：预计提速 **5-10x**
- 优化后后处理可降至 **1-2 ms**

### 与其他 ROI 模型对比

根据设备上现有模型的测试结果：

| 模型 | 输入尺寸 | 推理时间 | 相对性能 |
|------|---------|---------|---------|
| ROI320 Nano | 320×320 | ~8-10 ms | 基准 |
| **ROI160 (本模型)** | **160×160** | **12.36 ms** | **1.2-1.5x 慢** ⚠️ |
| ROI640 | 640×640 | ~25-30 ms | 2.5-3x 慢 |

**异常发现**：ROI160 应该比 ROI320 快，但实测更慢！

**可能原因**：
1. **Batch Size 影响**：
   - ROI160 设置为 batch=4
   - ROI320 可能是 batch=1
   - Batch 推理单帧时可能有调度开销

2. **模型结构差异**：
   - ROI160 是 P2-P3 双尺度（stride 4, 8）
   - ROI320 可能是 P3-P4-P5 三尺度（stride 8, 16, 32）
   - P2 尺度（40×40）计算量大于预期

3. **量化方式差异**：
   - 需要确认 ROI320 是否也用 split 模式

**建议验证**：
- 测试 batch=1 的 ROI160 模型性能
- 对比 P2-P3 vs P3-P4-P5 的计算量分布

## Batch Size 效率分析

### Batch=4 的性能收益

| 指标 | Batch=1 | Batch=4 | 提升倍数 |
|------|---------|---------|---------|
| 推理延迟 | 12.36 ms | 12.97 ms | 1.05x |
| 吞吐量 | 81 FPS | 308 FPS | 3.8x |
| 单帧成本 | 12.36 ms | 3.24 ms | 3.8x |

**效率评分**：⭐⭐⭐⭐⭐（5/5）

**结论**：
- Batch=4 几乎无额外延迟开销（仅+0.61ms）
- 吞吐量接近线性提升（理论 4x，实测 3.8x）
- **强烈推荐使用 batch 推理**

### Batch 推理适用场景

✓ **适合**：
- 视频流处理（批量帧）
- 多摄像头并发
- 离线批量处理
- 对延迟不敏感的应用

✗ **不适合**：
- 实时交互（需要最低延迟）
- 单摄像头实时流
- 延迟敏感应用（<15ms 要求）

## 优化建议

### 短期优化（立即可行）

1. **后处理加速**（预期提速 5-10x）
   ```
   - 使用 C++ 重写后处理
   - NEON 指令优化 sigmoid 和 decode
   - 优化 NMS 算法（快速 NMS、软 NMS）
   - 预期后处理降至 1-2 ms
   ```

2. **测试单核 NPU**
   ```
   - 当前使用 3 核（NPU_CORE_0_1_2）
   - 小模型可能单核更高效
   - 测试 NPU_CORE_0 的性能
   ```

3. **调整后处理参数**
   ```
   - 置信度阈值 0.25 → 0.3-0.4（减少候选框）
   - IoU 阈值 0.45 → 0.5-0.6（加速 NMS）
   ```

### 中期优化（需要重新转换）

1. **Batch=1 模型**
   ```
   - 为低延迟场景导出 batch=1 版本
   - 预期单帧延迟降至 8-10 ms
   ```

2. **输出格式优化**
   ```
   - 考虑合并输出（减少 4 个张量到 1-2 个）
   - 评估是否可以在 NPU 端做部分后处理
   ```

3. **混合量化评估**
   ```
   - 对关键层使用 FP16
   - 评估精度提升 vs 性能损失
   ```

### 长期优化（架构调整）

1. **模型轻量化**
   ```
   - 评估 P3-P4 双尺度（去掉 P2）
   - 减少 RepVGG 块数量
   - 知识蒸馏进一步压缩
   ```

2. **端到端 NPU 后处理**
   ```
   - 研究 RKNN 自定义算子
   - 在 NPU 上实现 decode + NMS
   - 消除 CPU-NPU 数据传输
   ```
